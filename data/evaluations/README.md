# Evaluation Outputs

This folder stores JSON outputs from `src.evaluate.run_evaluation`. Each file represents one evaluation run over a batch summary and includes aggregate scores, per-record judge results, token usage, latency, and estimated cost.

## What’s inside

Typical evaluation files contain:

- `run_name` — unique name for the evaluation run.
- `source_batch` — the batch summary that was evaluated.
- `judge_model` — the model used by the judge.
- `aggregates` — batch-level metrics and per-flaw-type breakdowns.
- `judge_cost_usd` — estimated judge cost for the run.
- `judge_tokens_total` — total judge tokens used.
- `load_stats` — stats about how many records were found and loaded.
- `results` — per-record judge outcomes.

## File pattern

Evaluation files are named like:

```text
eval_<batch_name>_<timestamp>.json
```

Example:

```text
eval_batch_openai_1per_1cand_20260803_145225_20260804_082354.json
```

## Dependency flow

Evaluation files depend on:

- `data/normalized/batches/*.json`
- `data/normalized/records/*.json`

The evaluation runner reads a batch summary, follows each `saved_path`, loads the corresponding normalized record JSON, and then scores each record with the judge.

## Generated by

```bash
python -m src.evaluate.run_evaluation <batch_summary_path> [limit]
```

Examples:

```bash
python -m src.evaluate.run_evaluation data/normalized/batches/batch_openai_1per_1cand_20260803_145225.json
python -m src.evaluate.run_evaluation data/normalized/batches/batch_openai_1per_1cand_20260803_145225.json 6
```

## How to read an evaluation JSON

### Aggregate block

The `aggregates` section summarizes:

- `items_evaluated`
- `items_scored`
- `items_parse_error`
- `items_runtime_error`
- `score_total_mean`
- `score_total_median`
- `score_total_min`
- `score_total_max`
- `high_quality_count`
- `high_quality_rate`
- `dimension_means`
- `flaw_type_breakdown`

### Per-record block

Each entry in `results` includes:

- `record_id`
- `status`
- `flaw_type`
- `difficulty`
- `score`
- `score_total`
- `notes`
- `error`
- `prompt_tokens`
- `completion_tokens`
- `latency_seconds`

## What to inspect first

When comparing runs, start with:

1. `items_scored` and `items_parse_error`.
2. `score_total_mean`.
3. `dimension_means`, especially `distractor_plausibility`.
4. `flaw_type_breakdown` to see whether one item family is lagging.
5. Per-record notes for the lowest-scoring items.

## Operational notes

- A successful evaluation does not necessarily mean the generator is perfect; it only means the judge found the batch acceptable under the current rubric.
- Repeated runs over the same source batch are useful for checking judge stability.
- If a batch summary points to missing files, `load_stats` will show that immediately.
- If the judge cannot parse the model output, the per-record status will be `parse_error`.
- If prompt building or model calls fail, the per-record status will be `runtime_error`.

## Related folders

- `data/normalized/batches/` — source batch summaries.
- `data/normalized/records/` — canonical records evaluated by the judge.
- `data/reports/` — older human-readable markdown reports.

## Notes

Keep this folder for evaluation artifacts that are still useful for comparison or regression checks. If you create a fresh frozen baseline and evaluation set later, older evaluation files can be pruned or archived to keep the repo lean.
